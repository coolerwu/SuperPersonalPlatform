# Multidisciplinary Critique Design

## Objective

Add a full-interactivity `多维批判` workspace where the user maintains academic
disciplines they understand, submits a question, receives parallel critiques from
the selected disciplines, and then receives a consolidated judgment from the same
configured prompt model.

The feature reuses the existing Harness prompt mode. It does not call a model
gateway directly and does not persist each discipline as a configured Agent.

## Product Flow

The page uses the selected `学科矩阵` direction and the existing restrained dark
command-center visual language.

- The discipline library stores a name, the user's known scope, a critique focus,
  and whether the discipline participates by default.
- Default disciplines are selected for every new question. The user may temporarily
  deselect a discipline without changing its saved default.
- A run fans the question out to every selected discipline in parallel.
- Each successful discipline result supplies four matrix fields: core assumption,
  counterevidence, opportunity cost, and key question.
- A consolidation prompt receives the successful discipline results and returns the
  weakest assumption, largest disagreement, and recommended validation.
- One failed discipline does not cancel successful disciplines. The page exposes
  the failed state and allows retrying that discipline. Consolidation proceeds when
  at least one discipline succeeds.
- Runs and their results are persisted as history in the active workspace.

## Domain Harness Request Factories

`HarnessRequest` gains explicit domain factories for its two legal shapes:

1. `HarnessRequest.for_prompt(...)` accepts an already-bound `Agent`, content,
   images, and an optional checkpoint callback. It never accepts tool context.
2. `HarnessRequest.for_agent(...)` accepts an already-bound `Agent`, content,
   optional images, resolved tool names, registry, runtime, checkpoint callback,
   and iteration limit. It validates that registry/runtime context is consistent
   with the resolved tool names.

The factories own request-shape invariants. Direct dataclass construction remains
an internal compatibility path for existing tests until callers migrate, but new
application code uses the factories.

Configuration binding remains in the application layer. `AgentChatService`
resolves configured Agent ids, model ids, skills, tools, image capability, and
runtime dependencies, then delegates legal request construction to the domain
factories. It does not duplicate request-shape validation.

For transient prompt calls, the critique service creates an in-memory
`AgentDefinition`, asks `AgentChatService` to resolve and validate the requested or
default `ModelDefinition`, creates the bound `Agent`, and delegates to
`HarnessRequest.for_prompt(...)`. Configuration loading does not move into the
Harness domain.

The builder does not accept a Harness mode override. `ModelDefinition.mode` remains
the single source of truth. A transient prompt request requires a model configured
with `mode=prompt`; an Agent-mode model is rejected with a clear configuration
error. Configuring the same upstream model for both modes requires two model
definitions, consistent with the existing model-driven Harness contract.

`AgentChatService.chat()` and `run_with_tool_runtime()` delegate request construction
to the domain factories before calling `run_agent()`. Application orchestration
services build already-bound transient Agents and schedule the returned requests.

## Critique Application Service

A dedicated application service owns discipline storage, critique history, prompt
templates, structured response parsing, and orchestration. It receives
`AgentChatService` for application-level model resolution and validation, while the
domain `HarnessRequest` factories enforce request shape.

For each run it:

1. Resolves the selected saved disciplines.
2. Builds one transient prompt `HarnessRequest` per discipline.
3. executes them concurrently with `asyncio.gather(..., return_exceptions=True)`.
4. Parses each response into the four matrix fields and records individual status.
5. Builds and executes a final transient prompt request for the consolidation judge.
6. Persists the completed or partially completed run.

Prompt responses use JSON objects with fixed keys. Parsing removes an optional
Markdown code fence, validates types and required fields, and treats invalid output
as a per-discipline failure rather than inventing missing analysis.

## Persistence

Workspace data lives under `critique/`:

- `disciplines.json` stores the user-managed discipline library.
- `runs/{run_id}.json` stores the question, selected discipline snapshots, per-run
  statuses and outputs, consolidated judgment, timestamps, and model id.

Runs store discipline snapshots so later edits do not rewrite historical meaning.
Writes use temporary files plus atomic replacement. IDs are generated by the
backend; user input never becomes a file path.

## API And Streaming

Authenticated `/api/critique/*` endpoints provide discipline CRUD, run history,
run detail, run creation, and failed-discipline retry.

Run creation uses a WebSocket so the UI can render per-discipline queued, running,
completed, and failed states plus the final judge state without polling. The initial
message contains the question and selected discipline ids. Server events contain
only stable run ids, discipline ids, status, parsed output, and safe error text.

## Frontend

The new `/critique` route appears in the existing sidebar as `多维批判` without a
duplicate global title block.

Desktop layout uses a question composer above a matrix, a collapsible discipline
library on the right, and a pinned consolidation panel below the matrix. Mobile
layout converts each discipline row into a single stacked result group while
preserving the four comparison labels.

The discipline editor contains `学科名称`, `我了解的范围`, `重点批判方向`, and
`默认参与`. Adding or editing a discipline changes future defaults only. Current
run selection is maintained separately in page state.

## Testing And Failure Handling

- Domain factory tests cover Prompt and Agent request shapes, tools, images, empty
  content, invalid registry/runtime combinations, and iteration limits.
- Application tests cover configured and transient prompt Agents, default and
  explicit model selection, and Agent-mode rejection.
- Service tests verify true concurrent fan-out, stable input ordering, partial
  failure, structured parsing, consolidation input, retry, and persistence.
- Route tests verify authentication, validation, WebSocket events, and safe errors.
- Frontend tests cover navigation, discipline CRUD, default versus temporary
  selection, progressive states, matrix results, partial failure, retry, history,
  and responsive rendering contracts.
- Existing Agent Chat and self-development tests ensure the builder refactor does
  not change configured Agent behavior.
